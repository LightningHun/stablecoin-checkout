## Reproduced findings

### G3-01 — Major / P1: malformed-response blocking is incomplete and not retained

Requirements: R04, R08, R11, R23; T11/T15. Architecture requires malformed data to be a protocol error that disables unsafe actions while preserving verified facts.

Locations: `src/features/checkout/infrastructure/paymentClient.ts:43` and `src/features/checkout/application/usePaymentController.ts:91`.

After a valid awaiting quote, return HTTP 200 with body `{broken`. `response.json()` executes outside the protocol-error `try`, so the raw SyntaxError is treated as an ordinary transport failure. Observed `health=stale`, `availability=usable`, and `canChange=true`. Separately, a syntactically valid unknown status correctly causes `availability=reconciling`, but a following HTTP 500 resets `protocolBlocked` to false without any accepted response; observed `availability=usable` again.

Required correction: classify successful-response JSON decoding failures as protocol errors, and retain a protocol block until a validated accepted response clears it. Preserve last-known payment state.

### G3-02 — Major / P1: creation HTTP 5xx is assumed to prove no mutation occurred

Requirements: R07, R11, R23; T15. The contract forbids another creation after an uncertain POST outcome.

Location: `src/features/checkout/application/usePaymentController.ts:250`–`267`.

After a valid initial quote, make a replacement POST return HTTP 500. The `status >= 400` condition excludes it from uncertainty handling. Observed `uncertain=false`, `availability=usable`, and `canChange=true`; the next selection issued another POST (create count increased from 2 to 3). A queued selection can take the same continuation path. HTTP 5xx does not establish whether an application mutation committed; old instructions can already have been superseded.

Required correction: treat mutation 5xx outcomes conservatively unless the contract explicitly proves non-execution, hide send instructions, and prevent automatic/manual new creation while uncertainty remains. Keep definitive 409 reconciliation separate.

### G3-03 — Major / P1: accepted snapshots can reduce received money and request more top-up

Requirements: R06, R09, R13, R23; T08/T11/T12. Architecture requires rejection of unexplained same-generation regressions, and amounts are snapshots rather than values to re-accumulate.

Location: `src/features/checkout/domain/paymentModel.ts:131`–`138`.

The reducer checks decreasing confirmations but does not compare received monetary facts. Both underpaid snapshots pass boundary validation: the first records received `120.00`, outstanding `43.69`; the second records received `100.00`, outstanding `63.69`, on the same reference/quote/generation. `acceptSnapshot` accepts the second. The transfer projection therefore asks for 20.00 more despite already verified receipt of that money.

Required correction: reject unexplained reductions in received amounts within a quote generation with exact scaled integer comparisons, retaining the earlier facts and blocking unsafe transfer instructions.

### G3-04 — Major / P1: quote pair metadata is not validated as a coherent transfer destination

Requirements: R02, R03, R04, R08, R23; T02/T04/T11.

Location: `src/features/checkout/infrastructure/responseSchemas.ts:27`–`37` (and catalogue schema at lines 8–25).

Keep `crypto_currency=USDT` and `network=tron`, but replace the quote's `network_name` with `Ethereum` and `crypto_address` with `0x1111111111111111111111111111111111111111`. `parsePayment` accepts the contradictory snapshot. Creation checks only the requested currency/network IDs, so it also has no guard against that name/address mismatch. Network identifiers, names, catalogue decimals, confirmation counts and network-specific address shapes are otherwise only loosely validated.

Required correction: validate supported pair metadata and address shape against the declared contract before accepting it, without recomputing authoritative `total_due`. Preserve the supplied source address rather than imposing an unsupported real-chain checksum requirement.

### G3-05 — Major / P1: mock forgets that a failed attempt previously received funds

Requirements: R07, R12, R23; T03/T08/T16. API_CONTRACT explicit decision 4 says replacement is only for an unfunded attempt and rejects replacement if funds were detected.

Location: `mock/server.ts:150`–`163`.

Over real HTTP: create the initial attempt, set demo state `detected`, set state `failed`, then POST another payment for the same order. Observed HTTP 201, reference `AQH-100307-PMT`; the previous reference is deleted by replacement. Checking `hasFunds(current.status)` loses the historical observation when status becomes `failed`, even though detected→failed is an allowed lifecycle transition.

Required correction: preserve an observed-funds fact for the attempt/order independently of its present status and reject destructive replacement once it has been set. Only the explicit demo reset should clear it. Keep the atomic check at mutation execution.

### G3-06 — Major / P1: offline resumption can retain usable instructions after clock continuity is lost

Requirements: R05, R10, R11, R23; T06/T07/T15. Architecture explicitly calls for re-anchoring on visibility/focus after suspension or clock discontinuity and using server confirmation when time is uncertain.

Locations: `src/features/checkout/infrastructure/ClockService.ts:20`–`24` and `src/features/checkout/application/usePaymentController.ts:294`–`302`.

With an injected clock, create a 900000 ms quote, then advance wall time 1000000 ms while monotonic time is paused. Dispatch focus and fail the reconciliation GET with a network error. Observed `remaining=900000`, `availability=usable`, `health=stale`. This simulates lost monotonic continuity during system suspension; no physical OS-sleep coverage is claimed. Focus calls GET but does not mark awaiting transfer instructions unavailable pending resynchronization, so offline recovery can continue displaying the old valid-time estimate indefinitely.

Required correction: mark awaiting transfer availability as reconciling when continuity/resumption needs a fresh sample, clear that guard only on an accepted response, and keep observed-funds states independent of the original quote deadline. Do not invent server expiry from an untrusted wall-clock jump.
