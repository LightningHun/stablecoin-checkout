# Running the checkout

Use Node 22.12 or newer (verified on 22.19.0), npm 10.9.3. Run `npm ci`, then `npm run dev`. The script starts Vite at http://127.0.0.1:5173 and the HTTP mock at http://127.0.0.1:8787; Vite proxies `/api`. Stop with Ctrl-C. Do not run dev and preview together on the default mock port.

For the built application: `npm run build`, then `npm run preview`. Preview serves http://127.0.0.1:4173 and starts the same mock. Set MOCK_PORT to another local port when concurrent isolated verification requires it. The browser stores the payment reference and an order-scoped pending-creation marker; payment amounts, addresses and status are restored from a fresh API response. The marker prevents a reload from repeating an initial POST whose outcome is unknown. It clears after verified initial merchant/order information, after an actual Continue payment reference is saved, or when the request is definitively rejected; this protection across reloads requires available browser storage. The mock still keeps payments only in memory: restarting it or resetting the demo removes them; an unknown saved reference is cleared and checkout starts fresh. Reset demo also clears this tab’s order reference and pending-creation marker. References are stored separately under `stablecoin-checkout:payment-reference:<ORDER_ID>`; a missing payment clears only its order’s key. The demo sends no real funds.

Open http://127.0.0.1:5173/?demo=1 to show evaluator controls below the shopper page. Create another order with **Create signed order link** in the demo panel, then open its returned `/?order=ORD-88214&sig=<16 lowercase hex>` URL. Registered orders can also use `?order=ORD-88214` while signatures are optional. A URL with neither `order` nor `sig` remains the default `ORD-88213` demo entry and makes no link-validation request. Any URL containing either parameter is checked by the server before catalogue loading or payment restoration. Each order restores independently across tabs and reopenings in the same browser storage. Opening the same order again restores its saved payment. A fresh page sends a normal payment request for the first listed currency/network but retains only merchant/order display information. Its reference, status, quote, address and deadline are discarded by the frontend: nothing is saved as a payment or polled before Continue. Reloading before Continue keeps the currency/network selector open. First Continue sends another normal request, even for the same pair, and uses only its new quote and reference. After Continue, reload restores that actual payment through GET. The backend has no delete endpoint; its original unfunded record is superseded by the later creation. References already stored by older versions remain restorable because their origin is ambiguous; use Reset demo explicitly to clear an old local test checkout. Expand Demo controls and set Order amount (EUR), then Apply amount: this configures the next created or requoted payment, while the current Total to pay stays tied to the accepted payment. Use Change, select a different currency/network pair, and Continue to create a replacement, or Get a new quote after expiry. Reset demo restores EUR 149.90. Choose a Payment state and Apply state; all eight API states are supported and each command targets this page’s order. Scenario commands update the backend only; they do not emit a refresh event or trigger an immediate payment GET. The page reads changes through its existing automatic polling (normally 2 seconds after the previous request finishes, with the existing error backoff and retry limits). Terminal payments and exhausted automatic retries do not restart polling when a demo command succeeds; use Reset demo for a new lifecycle or the existing Retry action when available. Reset demo retains its separate reset event and reload behavior. Order amount controls also apply only to this order. Connection controls choose Healthy, HTTP 500, Disconnect or Slow (5 seconds), then Apply connection. Advance 15 minutes advances the mock clock: awaiting quotes can expire, while detected/confirming payments gain one confirmation per selected network’s avg_confirmation_seconds until paid; ordinary waiting also progresses confirmations unless the mock clock is frozen. Reset demo is global: it removes all additionally registered orders and every payment/funds lock, retains only ORD-88213, and resets amounts, signature requirements, clock, metrics, and reference sequences. Other tabs discover missing payments on their next refresh or reload; terminal receipts need a reload. Reset before exploring a different terminal lifecycle. These controls intentionally bypass provider-like progression and are a local evaluation surface only.

Transaction hashes display as shortened links with an external-link icon. Hover to read the full hash. Ethereum opens Etherscan, Polygon opens PolygonScan, Tron opens TRONSCAN, and Solana opens Solscan in a new tab. The mock supplies full synthetic identifiers (not real on-chain payments), so explorer pages may report that the transaction was not found. Restart `npm run dev` after mock-code changes, then Reset demo to load the updated fixtures. Incomplete legacy hashes remain plain text because their missing characters cannot be recovered.

HTTP controls: POST `/api/demo/reset` with `{}` resets state; optional `now` (ISO), `freeze` (boolean) and `ttlMs` produce deterministic scenarios. Both reset and scenario accept `orderAmount`, a decimal string from "0.01" to "999999.99" with at most two decimal places, normalized to two decimals; invalid amounts return HTTP 400 with title "Invalid order amount" and leave state unchanged. Reset without `orderAmount` restores "149.90" for every order; a reset amount override configures only the default order, `ORD-88213`. POST `/api/demo/scenario` with `status`, `fault` (`none`, `500`, `disconnect`, `slow`), `delayMs`, `advanceMs`, or `orderAmount` controls the server. Scenario commands accept `order_id` (default `ORD-88213`) for payment status and order amount; faults, delays and time advances remain global. Order amount changes apply to that order’s next create/requote; current payments remain fixed. Quotes scale the literal demo principal proportionally to EUR 149.90 using integer arithmetic, rounded half up at the token scale, then add the unchanged network fee. GET `/api/currencies` returns only the currency catalogue; adding an order query parameter does not add merchant or order data. Those facts arrive in the normal payment response. GET `/api/demo?order_id=ORD-88214` exposes that order’s scenario and payment, global request metrics and mock time, plus an `orders` array of `{order_id, payment_reference, status, fundsObserved}` for all known orders. The plain demo URL also defaults to `ORD-88213`. The order registry starts with ORD-88213 only. POST `/api/demo/orders` with optional `{ "amount": "250.00" }` registers the next order and returns HTTP 201 with `order_id`, a 16-hex `sig`, and `checkout_url`. Catalogue, scenario and payment requests do not register unknown IDs; payment creation for an unknown order returns HTTP 400 `{ "title": "Unknown order" }`. GET `/api/demo` includes the complete order registry (including orders without payments), a top-level `requireSignature`, and the scenario flag. References remain globally unique until reset. Replacement invalidates only the same order’s unfunded attempt; observed funds block further creates/requotes for that order even after a later failed state. There is no shopper authentication or payment list page; order creation is a demo-only control. Controls bypass injected faults. Normal quotes last 15 minutes. For the requested quick browser expiry check, reset with `{ "ttlMs": 15000 }`; the committed real HTTP browser case verifies expiry and same-reference recovery after 15 seconds. Server responses include ISO `x-server-time` and `Cache-Control: no-store`.

Use `?locale=en-IE` or `?locale=de-DE` to inspect fiat formatting while retaining English UI. No real wallet, account, blockchain, provider affiliation or merchant return destination is configured. Invalid-link support uses the explicit demo address `mailto:help@payment-project.example`; it is an example address, not a live support service.

Checks: `npm run typecheck`, `npm run lint`, `npm run build`, `npm run test:unit`, `npm run test:component`, `npm run test:contract`, `npm run test:e2e`, and `npm run test:visual`. `npm run verify` aggregates ordinary checks; independent review and mutation evidence live in reports/gates. Browser setup: `npx playwright install chromium`. The browser suite opens an isolated headed Chromium window for the required two-minute background-tab observation; leave that test window alone until it closes. The separate expiry case uses 15 seconds.

For a formal isolated mutation audit, use `npm run test:mutation -- --candidate <reviewed-commit-sha> --g4-evidence reports/gates/G4.md`. It requires the exact Git candidate and recorded G4 clearance. `npm run test:mutation -- --candidate <commit-sha> --preflight` is development readiness only. Each defect is injected into an isolated archived copy and restored. Inspect the detailed result, including any surviving equivalent change, rather than treating an exit code alone as test-effectiveness approval.

Formal verification is separate from developer checks. README creation remains deferred by request.

## Invalid checkout links and demo signatures

GET `/api/checkout/link?order_id=<raw>&sig=<raw>` returns HTTP 200 for a definitive verdict. Valid replies contain `{ valid: true, order_id, checked_at }`. Invalid replies contain `{ valid: false, reason, order_id, checked_at, help_url }`; raw invalid order text is limited to 64 characters (or null when absent). Checks run in this order: malformed order code, unknown registered order, then signature. Responses include ISO `x-server-time` and `Cache-Control: no-store`. HTTP errors, a disconnected mock, timeouts and unparseable responses instead show the existing connection banner and Retry now; they never produce an invalid-link verdict. Retry repeats only validation until it succeeds.

Sample invalid URLs after Reset demo:

- http://127.0.0.1:5173/?order=ORD-99999 — unknown_order
- http://127.0.0.1:5173/?order=abc — malformed_order
- http://127.0.0.1:5173/?order=ORD-88213&sig=0000000000000000 — invalid_signature

Use **Create signed order link** to register a new order using the demo amount field and display/copy its URL. **Require signed links** sets the global `requireSignature` scenario flag. When enabled, explicit unsigned order URLs return missing_signature; issued signed links remain valid. The parameter-free demo entry still opens unchanged. A present but incorrect signature is rejected even when signatures are optional. Reset demo removes extra orders and returns the flag to false.

The signature is the first 16 lowercase hex characters of HMAC-SHA256 over the order ID with `MOCK_LINK_SECRET` from `backend/config.ts`. The fixed public demo secret is **not a security feature** and must not be treated as production authorization. Demo endpoints bypass injected faults, while the link-validation endpoint honors HTTP 500, disconnect and slow scenarios.

Invalid-link pages make one validation request, start no payment controller, read/write no payment persistence, and show no payment or demo controls. Copy details includes the reason text/code, order, server-supplied checked time formatted locally, and complete browser URL. Go back is shown when browser history exists. The Help link and closing share-details guidance are not displayed. The invalid page uses the existing demo footer and invents no payment-provider name.
